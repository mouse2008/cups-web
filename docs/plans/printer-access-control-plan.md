# 打印机访问控制实施计划

## 目标
为 LDAP 版 cups-web 增加“按打印机授权”的能力：
- 按角色整组控制可用打印机
- 按本地打印组批量控制可用打印机
- 按单个用户做例外放行或禁用
- 前端只展示当前用户可用的打印机
- 后端 `/api/print` 强制校验，防止绕过前端直接提交

## 当前现状
- 当前系统只有全局 `admin` / `user` 两种角色，没有打印机级 ACL。
- `/api/printers` 直接把 CUPS 全量打印机返回给所有已登录用户。
- `/api/print` 只检查登录态，没有校验“该用户是否允许使用目标打印机”。
- 用户体系已经支持 local + LDAP，同步后本地库里有稳定的 `users.id / username / role / ldap_uid / ldap_dn` 可用于授权。

## 建议的权限模型
### 主体（principal）
当前支持三类主体：
1. `role`：针对角色的整组授权，例如 `user`、`admin`
2. `group`：针对本地打印组授权，打印组成员可包含 LDAP 用户或本地用户
3. `user`：针对单用户授权，使用本地 `users.id` 作为主键引用

> 当前实现明确不依赖 LDAP 组；如果后续需要接 LDAP group，同样可以在现有 `subject_type` 模型上继续扩展。

### 规则（rule）
每条规则包含：
- `printer_uri`
- `subject_type`：`role` / `group` / `user`
- `subject_value`：角色名、打印组 ID 或用户 ID
- `effect`：`allow` / `deny`
- `created_at` / `updated_at`

### 判定规则
1. `admin` 默认允许全部打印机（后续如有需要再改为可配置）
2. 单用户规则优先于角色规则
3. 同层级内 `deny` 优先于 `allow`
4. 某台打印机如果**完全没有规则**，默认对普通登录用户开放
5. 某台打印机如果**存在任意规则**，则该打印机进入白名单模式：只有命中的 `allow` 且未被更高优先级 `deny` 覆盖时才允许

这个模型能满足“按角色整组控制 + 对单用户做例外调整”。

## 拆分任务
### Task 01：数据层 + 授权判定服务
- 新增 ACL 表及 migration
- 新增 store CRUD / list helpers
- 新增授权判定服务（列出可见打印机、校验单台打印机是否可打印）
- 增加单元测试，覆盖 allow/deny 优先级

### Task 02：后端 API 接入
- `/api/printers` 改为只返回当前用户可用打印机
- `/api/print` 打印前强制检查权限，未授权返回 403
- 新增管理员 API：查看/保存某台打印机的 ACL 配置
- 为新 API 补 handler 测试

### Task 03：管理端 UI
- 在管理员界面新增“打印机权限”配置区
- 支持按打印机查看当前规则
- 支持添加角色规则、用户规则、allow/deny 调整
- 支持 LDAP 用户搜索/筛选（可先做本地用户名筛选，再逐步增强）

### Task 04：打印页联调与验收
- 打印页只显示当前用户可选打印机
- 当用户失去权限时，历史已选打印机自动回退
- 联调 LDAP 用户、管理员、普通用户的行为
- 补充 README / 运维说明

## 风险与注意点
- 当前只有 `admin/user` 两种角色；如果后续要更细角色，需同步扩展用户管理。
- 如果直接用用户名做 user rule，后续改名会有迁移成本，所以建议 user 规则引用 `users.id`。
- 管理端选择单用户时，需要避免把“已删除/LDAP 已失效”用户继续挂在规则里，建议 UI 标识无效用户。
- 需要保证 `/api/print` 的后端校验先落地，否则前端隐藏打印机没有安全意义。

## 验收标准
- 普通用户只能看到自己被允许的打印机
- 未授权用户直接 POST `/api/print` 会收到 403
- 管理员可按角色授权打印机，并对单个用户做 allow/deny 覆盖
- 单元测试覆盖主要优先级分支
